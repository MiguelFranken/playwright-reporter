title: REST API
description: Read runs, results, tests and verdicts, and manage test cases and visual review, from scripts, CI and your own tools.
---

Every instance serves a REST API under `/api/v1`. It answers from the same code as the
[MCP server](/docs/ai-assistants): the same projects, the same verdicts, the same errors. Every MCP tool has an
endpoint — reads are `GET`s, and the tools that change data are `POST` or `PATCH` requests.

```bash
curl -H "Authorization: Bearer $PW_REPORTER_PAT" \
  "https://reporter.example.com/api/v1/projects/acme/web/runs?status=failed&branch=main&limit=5"
```

| | |
| --- | --- |
| Base URL | `https://<your instance>/api/v1` |
| Authentication | A personal access token, `Authorization: Bearer pwr_pat_…`. See [Authentication](/docs/api/authentication). |
| Format | JSON. Dates are ISO 8601 strings. Errors are problem details. See [Errors and limits](/docs/api/errors-and-limits). |
| Description | OpenAPI 3.1, at `/api/v1/openapi.json` on your instance, with its own URL as the server. |
| Versioning | Changes within `v1` only add. A breaking change would get `/api/v2`. |

## Addressing things

Projects are addressed by their slugs, as in the app's URLs: `/projects/{team}/{project}`. Inside a project:

- a **run** by its number (`128`), its id, `latest` or `latest-failed` — `latest` can be scoped with `branch` and
  `environment`;
- a **result** (one test in one run), a **test** (across runs) and an **attachment** by their ids, which other
  answers return.

Every object carries a `url` into the app, for the full picture.

## Endpoints

| | |
| --- | --- |
| `GET /me`, `GET /projects` | The token, and what it can read. |
| `…/filters`, `…/health` | Filter values, and where the project stands. |
| `…/runs`, `…/runs/{run}`, `…/runs/{run}/results` | Runs and their results. |
| `…/results/{result}`, `…/attachments/{attachment}` | One result in full, one attachment. |
| `…/tests`, `…/tests/{test}` | Tests across runs, and one test's history. |
| `…/runs/{run}/failure-groups`, `…/runs/{run}/compare`, `…/runs/{run}/rerun-command`, `…/results/{result}/failure-context`, `…/tests/{test}/flakiness`, `…/tests/{test}/verify-fix` | Diagnostics. |
| `…/test-cases`, `…/test-cases/{case}`, `…/test-suites`, `…/uncovered-tests` | [Test cases](/docs/using/test-cases), one case with its linked tests, the suite tree, and the Playwright tests no case covers yet. |
| `…/runs/{run}/review-checkpoints`, `…/review-captures/{capture}` | A run's [review checkpoints](/docs/using/visual-review), and one image with its baseline, its comment threads and a link to it with the threads drawn on as numbered pins. |
| `…/review-threads` | The [comment threads](/docs/using/visual-review#comments) of a run's (or one image's) review images, by pin number, with where each points. |
| `…/library`, `…/library/flows` | The [library](/docs/using/visual-review#the-library)'s references, and one reference's flows. |

`…/runs/{run}/results` takes the run page's filters too: `outcome`, `file`, `search`, `browser`, `tag`, `retried`,
and `artifact` — `screenshot`, `video` or `trace` for tests with one, `no-screenshot`, `no-video` or `no-trace` for
tests without. Repeat a parameter for several values (`tag=@smoke&tag=@checkout`).

## Changing data

The endpoints that change data take a JSON body and need a token with the `write` scope (see
[Authentication](/docs/api/authentication)). Your role in the team still decides: a viewer's token cannot change
anything, and a change the role may not make answers `404`, like a project the token cannot see.

| | |
| --- | --- |
| `POST …/test-cases`, `PATCH …/test-cases/{case}` | Create a test case (`201`, with its new key), or change some of its fields. Each edit is a new version; pass `expectedVersion` to refuse an edit if the case changed since you read it. |
| `POST …/test-cases/bulk` | Apply one change to up to 200 cases (`cases`: keys or ids): their priority, status, severity, type, behavior, automation, suite, muting or tags. |
| `POST …/test-cases/{case}/links` | Link Playwright tests (by test id) to a case, or unlink them. |
| `POST …/test-cases/adopt` | Turn Playwright tests into linked test cases (`201`): `tests` into one suite or suites mirroring their files, or `placements` with a suite and title per group. |
| `POST …/test-suites`, `POST …/test-suites/delete-empty` | Create a suite (`201`), or delete suites that hold no cases. |
| `POST …/review-captures/decisions` | Approve review checkpoint images, or ask for changes with a comment (and, on one image, pins). |
| `POST …/review-threads`, `POST …/review-threads/status` | Pin a comment on a review image (at a spot or area, in percent) or reply to a thread; resolve or reopen one. |
| `POST …/library/references` | Keep a branch or pull request in the library, pin its run, make it the default — or take it out. |

```bash
curl -X POST -H "Authorization: Bearer $PW_REPORTER_PAT" -H "Content-Type: application/json" \
  -d '{"title": "Pay by card", "suite": "Checkout / Payment", "priority": "high"}' \
  "https://reporter.example.com/api/v1/projects/acme/web/test-cases"
```

Priorities are `critical`, `high`, `medium`, `low` and `none`. Change one case's, or many at once:

```bash
curl -X PATCH -H "Authorization: Bearer $PW_REPORTER_PAT" -H "Content-Type: application/json" \
  -d '{"priority": "critical"}' \
  "https://reporter.example.com/api/v1/projects/acme/web/test-cases/TC-12"

curl -X POST -H "Authorization: Bearer $PW_REPORTER_PAT" -H "Content-Type: application/json" \
  -d '{"cases": ["TC-12", "TC-14", "TC-15"], "priority": "high"}' \
  "https://reporter.example.com/api/v1/projects/acme/web/test-cases/bulk"
```

The [library](/docs/using/visual-review#the-library) filters and groups flows by the highest priority of their test
cases, so this is also how a team decides what its reviewers look at first.

A suite is given by its id or by its path of names from the top (`Checkout / Payment`); a missing level is created.

The **Reference** section documents every parameter and field, generated from the code.

## Pagination

Lists take `limit` (1–100, default 20) and answer with `total` and an opaque `nextCursor`. Pass it back as `cursor`,
with the other parameters unchanged, for the next page; `null` means there is none.
