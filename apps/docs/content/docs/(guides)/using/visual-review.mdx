---
title: Visual review and the library
description: Review what every flow looks like, desktop beside mobile, approve only what changed — and keep a library of the product's screens for everyone.
---

Your Playwright tests already walk through every flow of the product. **Visual review** has them take a named
screenshot at each milestone — the form filled in, the price after a coupon, the confirmation — once per variant, and
lays those checkpoints out as a storyboard: one row per test, the milestones left to right in the order they
happened, desktop beside mobile.

An approval holds for the exact pixels. When the next run captures the same image, it is already approved; only images
that changed, and checkpoints nobody approved yet, wait for a reviewer. A run where nothing changed asks for nothing.

The same screens serve two purposes, with a place each in the sidebar:

- **Visual Review** is for changes: what a pull request or branch changed on screen, and the decision about it.
- **Library** is documentation: every flow of the product, screen by screen, as a branch or pull request shows it.
  Nobody has to set up data, fake a booking or know the way through the app to see a screen — which makes it as
  useful to a product owner or a support team as to the developer who changed it.

## Capturing checkpoints

Add the `review` fixture from `@miguelfranken/reporter/review` to your test, and call it once the state you want to
review is asserted:

```ts title="tests/fixtures.ts"
import { test as base } from '@playwright/test';
import { reviewFixtures, type ReviewFixture } from '@miguelfranken/reporter/review';

export const test = base.extend<{ review: ReviewFixture }>(reviewFixtures());
```

```ts title="tests/checkout.spec.ts"
import { expect } from '@playwright/test';
import { test } from './fixtures';

test('places an order', async ({ page, review }) => {
  // …add to the cart, fill in the form…
  await expect(page.locator('#total')).toHaveText('$157.00');
  await review('checkout-ready', { title: 'Checkout filled in', description: 'Every field complete, before submitting.' });

  await page.getByRole('button', { name: 'Place order' }).click();
  await expect(page.getByRole('heading', { name: 'Thank you for your order!' })).toBeVisible();
  await review('order-confirmation', { title: 'Order confirmation' });
});
```

Each call captures the page at a desktop (1280 × 720) and a mobile (390 × 844) viewport, full page, and restores the
viewport afterwards. Before each capture it waits for web fonts, scrolls through the page so lazy and scroll-revealed
content loads, turns off animations and hides the caret. The name is the checkpoint's identity across runs: keep it
stable, and short (`coupon-applied`, `booking-confirmation`).

Pick milestones a person should look at: a complete form before submitting, a recalculated price, a meaningful error,
the final result. Two or three per happy path are plenty; a spinner or every click is noise.

### Options

`reviewFixtures(config)` sets the defaults, and each `review(name, options)` call can override them.

| Option | Default | What it does |
| --- | --- | --- |
| `variants` | desktop and mobile | Viewports to resize to, as `[{ name, viewport: { width, height } }]`. `'project'` captures once, as the running Playwright project: use it with one project per device to review real device emulation (touch, mobile user agent). |
| `fullPage` | `true` | The whole scrollable page. Use `false` for dialogs, drawers and other fixed overlays, which a full-page capture would repeat down the page. |
| `scale` | `'device'` | Pixels at the device scale factor (2× on a retina config), or `'css'` for one per CSS pixel. |
| `style` | | CSS applied only while the screenshot is taken: pin a sticky header, hide a cookie banner. A function gets the page. |
| `mask` | | Elements painted over, such as generated ids or timestamps, so they never make an unchanged page look changed. |
| `beforeCapture` / `prepareViewport` | | Runs after each resize, before the capture: reopen a menu that closed at the new breakpoint. |
| `thumbnails` | `true` | Also attach a small JPEG of the first viewport, which the storyboard shows. |
| `title`, `description`, `kind`, `tags`, `flow` | | Per checkpoint: what a reviewer sees next to the image. |

Emails and other HTML render into the page with `review.html(name, html)`, captured the same way.

Set `PW_REVIEW_SCREENSHOTS=off` to skip every capture, for example in a fast local loop.

### What gets sent

Each checkpoint attaches its images as `review:<name>:<variant>`, a preview of each, and a small record: the order, the
title, the URL and page title, the viewport and scale, and a hash of every image. The reporter adds the steps the
capture ran inside and the moment it happened, so the app can take you to that point in the video.

A suite that already attaches its own screenshots named `review:<name>:<variant>` gets checkpoints too, without the
helper: the reporter reads the names, hashes the images and takes the steps and times from the report. Runs ingested
before visual review existed are read the same way.

Other reporters see the images as ordinary attachments; `readCheckpoints(result)` from the same module gives them the
records.

## Reviewing

A run with checkpoints has a **Visual review** button on its page, with how many images still need review. The
storyboard opens on those: **Changed** images differ from the approved one, **New** ones were never approved. Filter by
status or variant, or search for a test, a test case key or a checkpoint.

The folders on the left organize the flows the way [test cases](/docs/using/test-cases) do: under **Test Cases**, a test
linked to a case sits in that case's suite, and tests no case covers are in **Not in a test case**, by spec file.
Switch to **Files** to browse by spec file instead. Folders open and close like the Test Cases tree. Each folder shows
how many images below it still need review. A flow links to its test cases, and a test case's page shows the screens
of its linked tests.

Every capture is shown on a screen of its own shape — a phone is portrait, a desktop wide — and the size slider scales
them all. From about a quarter of the real size the screens load the full image and scroll, so a flow can be read
without opening it. The size is remembered in your browser.

Open a checkpoint to see it on a screen you set like a browser's device toolbar: **As captured** (each variant's own
viewport), a preset (desktop, laptop, tablet, iPhone) or any width × height, at a zoom that fits the window or a fixed
percentage. The page scrolls inside the screen. Compare every variant side by side, or a variant with its approved baseline — side by
side, with a slider, as a **Difference** (identical pixels turn black, every change lights up) or as an overlay. Next
to it: the steps it was captured in, the URL, the viewport, and a link to the moment in the video.

| Key | Does |
| --- | --- |
| <kbd>←</kbd> <kbd>→</kbd> | Previous / next checkpoint |
| <kbd>↑</kbd> <kbd>↓</kbd> | Previous / next test |
| <kbd>V</kbd> | Next variant |
| <kbd>C</kbd> | Next comparison mode |
| <kbd>A</kbd> | Approve, and go to the next image that needs review |
| <kbd>R</kbd> | Write a change request |

**Approve test** and **Approve … shown** approve many images at once. **Request changes** keeps a comment next to the
image, for whoever fixes it — a person or an [AI assistant](/docs/ai-assistants/tools).

Admins and members can decide; viewers can look.

## The review queue

**Visual Review** in the sidebar lists what waits for a reviewer, one row per pull request or branch: its newest run,
how many of that run's images changed or are new, and how many earlier runs it superseded (only the newest run of a
change needs anyone). It opens on the changes that wait; **All changes** shows the rest. Each row links to the pull
request or branch, and says when it is kept in the library.

A pull request's and a branch's own page has a **Screens** card too: what its newest run asks of a reviewer, and its
place in the library.

## The library

**Library** in the sidebar shows the product's flows as documentation: the same storyboard and viewer, without
statuses, comparisons or approvals, with each checkpoint's description under its title. It opens on the **default
reference** — the default branch, unless you chose another — and the picker at the top switches to any branch or pull
request kept in the library.

A reference shows either:

- **its newest run**: every test as the newest run on that branch or pull request captured it, so a run of only some
  tests does not hide the others, and a checkpoint a test no longer takes disappears; or
- **a pinned run**: exactly that run, whatever runs next. Pin the run of a release to document what customers see.

Keep a branch or pull request from the library's **Add to library**, from its own page (**Keep in library**), or pin
a run from its review (**Pin to library**). A long-lived pull request can stay in the library while it is open, so
everyone can see the product state it builds. **Library settings** give a reference a name and a sentence for readers
who do not know the branch ("Checkout redesign"), choose its version, and make it the default: the library opens on
it, and test case pages show its screens.

Admins and members can change the library; viewers browse it. Links to a reference (`/library?ref=pr:212`) work for
references nobody kept, too.

The approved image of each checkpoint is its baseline and is kept by the
[artifact retention](/docs/administration/retention) policy, however old it is — as are the screens the library shows,
and the runs pinned in it.

## For AI assistants

`list_review_checkpoints` answers what changed in a run, `get_review_checkpoint` attaches an image with its baseline
so the assistant can look at it, and — with a write-scoped token — `review_checkpoint` approves or asks for changes.
An agent that changed the UI can check its own work before you do.

`list_library` names the references in the library and the run each shows; `get_library_flows` lists a reference's
flows and checkpoints, with capture ids to look at, and the link to hand a person. With a write-scoped token,
`set_library_reference` keeps a pull request in the library, pins its run or makes it the default. The REST API has
the same reads under `/runs/{run}/review-checkpoints`, `/review-captures/{capture}`, `/library` and `/library/flows`.
