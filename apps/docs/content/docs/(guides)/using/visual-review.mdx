---
title: Visual review and the library
description: Review what every flow looks like, desktop beside mobile, approve only what changed — and keep a library of the product's screens for everyone.
---

Your Playwright tests already walk through every flow of the product. **Visual review** has them take a named
screenshot at each milestone — the form filled in, the price after a coupon, the confirmation — once per variant, and
lays those checkpoints out as a storyboard: one row per test, the milestones left to right in the order they
happened, desktop beside mobile.

An approval holds for the exact pixels. When the next run captures the same image, it is already approved; only images
that changed, and checkpoints nobody approved yet, wait for a reviewer. A run where nothing changed asks for nothing.
Every changed image is also **measured** against the approved one, pixel by pixel: how much changed and where, so the
viewer takes you straight to the change — and noise nobody can see is approved for you.

The same screens serve two purposes, with a place each in the sidebar:

- **Visual Review** is for changes: what a pull request or branch changed on screen, and the decision about it.
- **Library** is documentation: every flow of the product, screen by screen, as a branch or pull request shows it.
  Nobody has to set up data, fake a booking or know the way through the app to see a screen — which makes it as
  useful to a product owner or a support team as to the developer who changed it.

## Capturing checkpoints

Add the `review` fixture from `@miguelfranken/reporter/review` to your test, and call it once the state you want to
review is asserted:

```ts title="tests/fixtures.ts"
import { test as base } from '@playwright/test';
import { reviewFixtures, type ReviewFixture } from '@miguelfranken/reporter/review';

export const test = base.extend<{ review: ReviewFixture }>(reviewFixtures());
```

```ts title="tests/checkout.spec.ts"
import { expect } from '@playwright/test';
import { test } from './fixtures';

test('places an order', async ({ page, review }) => {
  // …add to the cart, fill in the form…
  await expect(page.locator('#total')).toHaveText('$157.00');
  await review('checkout-ready', { title: 'Checkout filled in', description: 'Every field complete, before submitting.' });

  await page.getByRole('button', { name: 'Place order' }).click();
  await expect(page.getByRole('heading', { name: 'Thank you for your order!' })).toBeVisible();
  await review('order-confirmation', { title: 'Order confirmation' });
});
```

Each call captures the page at a desktop (1280 × 720) and a mobile (390 × 844) viewport, full page, and restores the
viewport afterwards. Before each capture it waits for web fonts, scrolls through the page so lazy and scroll-revealed
content loads, turns off animations and hides the caret. The name is the checkpoint's identity across runs: keep it
stable, and short (`coupon-applied`, `booking-confirmation`).

Pick milestones a person should look at: a complete form before submitting, a recalculated price, a meaningful error,
the final result. Two or three per happy path are plenty; a spinner or every click is noise.

### Options

`reviewFixtures(config)` sets the defaults, and each `review(name, options)` call can override them.

| Option | Default | What it does |
| --- | --- | --- |
| `variants` | desktop and mobile | Viewports to resize to, as `[{ name, viewport: { width, height } }]`. `'project'` captures once, as the running Playwright project: use it with one project per device to review real device emulation (touch, mobile user agent). |
| `fullPage` | `true` | The whole scrollable page. Use `false` for dialogs, drawers and other fixed overlays, which a full-page capture would repeat down the page. |
| `scale` | `'device'` | Pixels at the device scale factor (2× on a retina config), or `'css'` for one per CSS pixel. |
| `style` | | CSS applied only while the screenshot is taken: pin a sticky header, hide a cookie banner. A function gets the page. |
| `mask` | | Elements painted over, such as generated ids or timestamps, so they never make an unchanged page look changed. |
| `beforeCapture` / `prepareViewport` | | Runs after each resize, before the capture: reopen a menu that closed at the new breakpoint. |
| `thumbnails` | `true` | Also attach a small JPEG of the first viewport, which the storyboard shows. |
| `title`, `description`, `kind`, `tags`, `flow` | | Per checkpoint: what a reviewer sees next to the image. |

Emails and other HTML render into the page with `review.html(name, html)`, captured the same way.

Set `PW_REVIEW_SCREENSHOTS=off` to skip every capture, for example in a fast local loop.

### What gets sent

Each checkpoint attaches its images as `review:<name>:<variant>`, a preview of each, and a small record: the order, the
title, the URL and page title, the viewport and scale, and a hash of every image. The reporter adds the steps the
capture ran inside and the moment it happened, so the app can take you to that point in the video.

A suite that already attaches its own screenshots named `review:<name>:<variant>` gets checkpoints too, without the
helper: the reporter reads the names, hashes the images and takes the steps and times from the report. Runs ingested
before visual review existed are read the same way.

Other reporters see the images as ordinary attachments; `readCheckpoints(result)` from the same module gives them the
records.

## Reviewing

A run with checkpoints has a **Visual review** button on its page, with how many images still need review. The
storyboard opens on those: **Changed** images differ from the approved one, **New** ones were never approved. Filter by
status or variant, or search for a test, a test case key or a checkpoint.

The folders on the left organize the flows the way [test cases](/docs/using/test-cases) do: under **Test Cases**, a test
linked to a case sits in that case's suite, and tests no case covers are in **Not in a test case**, by spec file.
Switch to **Files** to browse by spec file instead. Folders open and close like the Test Cases tree. Each folder shows
how many images below it still need review. A flow links to its test cases, and a test case's page shows the screens
of its linked tests.

Every capture is shown on a screen of its own shape — a phone is portrait, a desktop wide — and the size slider scales
them all. From about a quarter of the real size the screens load the full image and scroll, so a flow can be read
without opening it. The size is remembered in your browser.

Open a checkpoint to see it on a screen you set like a browser's device toolbar: **As captured** (each variant's own
viewport), a preset (desktop, laptop, tablet, iPhone) or any width × height, at a zoom that fits the window or a fixed
percentage. The page scrolls inside the screen. Compare every variant side by side, or a variant with its approved baseline — side by
side, with a slider, as a **Difference** (identical pixels turn black, every change lights up) or as an overlay. Next
to it: the steps it was captured in, the URL, the viewport, and a link to the moment in the video.

**Compare with** chooses the image a variant is compared with. **Automatic** uses the approved baseline, or the run
before when nothing is approved yet. You can also pick one of these:

- **Approved baseline** or **Run before**.
- **Latest open comments**: the newest earlier image that still has unresolved comments, so you can check whether
  they were fixed. Side by side, its pins sit where they were placed.
- Any of the last ten runs that captured the screen. Every earlier image with open comments is listed too, however
  old, with the number of open comments. Resolved comments are not counted.

Only images that are still stored are offered. When the [retention policy](/docs/administration/retention)
has deleted a run's screenshots, that run is left out of the list, and **Run before** is the newest earlier run that
still has its image. The list of other runs loads when you open the menu.

Your choice stays as you move from checkpoint to checkpoint, and it is part of the link (`against=previous`,
`against=run:38`). Where it finds nothing, for example a run that did not capture this screen, the viewer says so
and shows the automatic comparison. The difference to the chosen image is measured the first time you open it.

| Key | Does |
| --- | --- |
| <kbd>←</kbd> <kbd>→</kbd> | Previous / next checkpoint |
| <kbd>↑</kbd> <kbd>↓</kbd> | Previous / next test |
| <kbd>V</kbd> | Next variant |
| <kbd>M</kbd> | Next comparison mode |
| <kbd>N</kbd> <kbd>P</kbd> | Next / previous measured change |
| <kbd>A</kbd> | Approve, and go to the next image that needs review |
| <kbd>C</kbd> | Comment mode: click to pin a comment, drag to mark an area |
| <kbd>1</kbd> – <kbd>8</kbd> | In comment mode: pin, area, pen, highlighter, arrow, rectangle, ellipse, eraser |
| <kbd>⌘</kbd> <kbd>Z</kbd> | In comment mode: take back the last shape drawn, or the last erasing |
| <kbd>R</kbd> | Comment on the whole image |
| <kbd>[</kbd> <kbd>]</kbd> | Previous / next comment |
| <kbd>E</kbd> | Resolve or reopen the open comment |
| <kbd>H</kbd> | Hide or show the pins |

### Measured changes

When a run finishes, each image that differs from its approved baseline (or, before anything is approved, from the
run before) is compared pixel by pixel, in the background. The comparison ignores anti-aliasing — a font edge
rendered a shade differently is not a change — and groups what really changed into **regions**.

- On the storyboard each measured screen gets a badge (**0.4%**, **No visible change**) and boxes around its changes.
  **Most changed first** ranks the tests by their largest change, across every folder.
- The viewer opens a measured image on **Changes**: this run's image with the changed pixels in red, a numbered box
  per region, and a pager (<kbd>N</kbd> / <kbd>P</kbd>) that scrolls from one to the next. A page taller than the
  screen gets a strip beside it that shows where on the page the changes are.
- The side panel says how many pixels changed, in how many regions, and whether the page changed size. When content
  was inserted or removed (a banner near the top), the rest of the page only moved: the panel says how many pixels were
  added or removed and where, so a pushed-down page is not mistaken for a changed one.
- An image too large to measure (over 40 megapixels by default) still has every comparison by eye.

A checkpoint whose image has a part that always differs — a clock, a rotating promotion — can **leave out areas**:
open it, choose **Leave out areas**, and drag rectangles over the image. They hold for that checkpoint and variant in
every later run, and the image is measured again without them. (Better still, when you can: `mask` them in the test.)

### Approved within tolerance

A changed image whose measured change is within the project's **tolerance** is approved automatically, with the
numbers as the reason ("Within the project's diff tolerance: no visible change against the approved image of run
#470"). It shows as **Auto-approved**, and like any approval it holds for those exact pixels. The baseline stays the
image a person approved, so small changes cannot add up, approval by approval, into a large one nobody looked at.

By default the tolerance approves only images with **no visible change at all** — the same pixels in a different PNG
encoding, or differences anti-aliasing explains — which is always safe. **Project settings → Visual comparison**
can allow a number of changed pixels or a share of the image, turn automatic approval off, and make the comparison
more or less sensitive to colour. A page that changed size is never within the tolerance.

**Approve test** and **Approve … shown** approve many images at once. **Request changes** records that the image needs
work; point at what should change with comments.

### Comments

Comments sit on the screenshot, where the change belongs, like comments in Figma. Press <kbd>C</kbd> (or **Comment**)
and, with the **pin**, click a spot to drop a numbered pin — or pick the **area** and drag over what you mean; write
what should change and press <kbd>Enter</kbd>. Hover a pin to read its thread, click it to keep it open, reply under
it, and resolve it with ✓ once it is done. From the keyboard, focus the screenshot in comment mode, press
<kbd>Enter</kbd> for a crosshair, move it with the arrow keys and press <kbd>Enter</kbd> again (with the area, once at
each corner). **Comment on the whole image** starts a thread without a pin.

When a pin or an area does not say it, draw. Comment mode puts a tool bar over the screenshot: besides the pin and the
area, a **pen**, a **highlighter**, an **arrow**, a **rectangle** and an **ellipse**, in six named colours — red,
orange, yellow, green, blue and purple (the colours show while a drawing tool is picked). Drawings stand on their own:
each shape is saved as you let go, with no comment to write, and everyone looking at the image sees it — so a comment
can say "the blue area should be larger, the yellow one smaller" about what is drawn beside it. Lines are steadied as
you draw; hold <kbd>Shift</kbd> to keep an arrow at 45° steps, or to draw a square or a circle. The **eraser** takes
away a drawing you click, or every drawing you drag across: your own, or anyone's for a project admin. <kbd>⌘</kbd>
<kbd>Z</kbd> takes back what you drew or erased. A drawing belongs to the pixels it was drawn on: it shows on every
run with the same image, and stays with that version once the image changes. AI assistants see drawings too:
`get_review_checkpoint` draws them on the image it sends, under the pins, and lists them shape by shape, with the
colour, who drew it and where it is.

The panel beside the image lists every thread by its number — open ones first, with **Resolved** and **All** a click
away — and a row opens its pin. The storyboard shows how many comments are open on each screen. A thread's number stays
the same, and a link to it (`…/review?cp=…&v=desktop&thread=3`) opens the viewer at its pin.

A thread belongs to the image — the checkpoint and variant — not to one run. While it is open it shows on later runs'
captures too: where the pixels are the same, exactly where it was placed; where the image changed since, with a dashed
pin that says it was placed on an earlier run. That is how a change request reaches the run that fixes it, and the
reviewer resolves it there: a screen with such comments opens on the first of them — the image the comment was made
on, with its pin and the comment, beside the screen as it is now — and **Fixed — resolve** (<kbd>E</kbd>) goes on to the
next. <kbd>O</kbd> switches between that comparison and the screen. A screen that changed never resolves a comment by
itself. Approving an image with open comments asks whether to resolve them. While a thread is open,
the retention policy keeps the whole flow it was placed on — every checkpoint of that test in that run — unless an admin
lets these visuals expire.

Admins and members can decide; everyone in the team, viewers included, can comment. You can edit and delete your own
comments, and admins can delete anyone's; deleting a thread's first comment deletes the thread.

## The review queue

**Visual Review** in the sidebar lists what waits for a reviewer, one row per pull request or branch: its newest run,
how many of that run's images changed or are new, and how many earlier runs it superseded (only the newest run of a
change needs anyone). It opens on the changes that wait; **All changes** shows the rest. Each row links to the pull
request or branch, and says when it is kept in the library.

A pull request's and a branch's own page has a **Screens** card too: what its newest run asks of a reviewer, and its
place in the library.

## The library

**Library** in the sidebar shows the product's flows as documentation, and the feedback on them: the same storyboard
and viewer, without approvals, with each checkpoint's description under its title. It opens on the **default
reference** — the default branch, unless you chose another — and the picker at the top switches to any branch or pull
request kept in the library.

A reference shows either:

- **its newest runs**: every checkpoint and variant as the newest run on that branch or pull request captured it. A
  full run updates every screen; a run of only some tests — or a test that failed half way — updates what it captured
  and leaves every other screen as it was, marked with the run it comes from. A checkpoint disappears only once a later
  run of its test passed without capturing it; or
- **a pinned run**: exactly that run, whatever runs next. Pin the run of a release to document what customers see.

Keep a branch or pull request from the library's **Add to library**, from its own page (**Keep in library**), or pin
a run from its review (**Pin to library**). A long-lived pull request can stay in the library while it is open, so
everyone can see the product state it builds. **Library settings** give a reference a name and a sentence for readers
who do not know the branch ("Checkout redesign"), choose its version, and make it the default: the library opens on
it, and test case pages show its screens.

### Reviewing in the library

Every screen has a state in the review loop, and the four counts above the flows filter to one of them:

| State | Means | Whose turn |
| --- | --- | --- |
| **Waiting for changes** | An open comment (or change request) on the screen as it is now. | A developer's |
| **Ready to verify** | An open comment made on an earlier version: the screen changed since. | The reviewer's: compare, then resolve |
| **Needs review** | Differs from the approved screen, or nobody approved it, and nobody commented. | A reviewer's |
| **Updated** | Changed since the capture before it on this branch. | Anyone curious |

The loop: tests run and upload their screens; reviewers comment where something should change; developers fix it —
in as many small commits as they like — and run just the affected tests; the changed screens turn **Ready to verify**,
and the reviewer compares each with the version they commented on and resolves the comment. **Feedback** lists every
open comment of the flows shown, what waits and what can be verified, and opens the viewer at its pin.

**Resolve feedback** goes through that feedback one item after another, across screens and flows, in the order of the
journeys — the flows shown, so a folder or a search narrows it (a folder's menu has **Resolve feedback here** too). Every
comment opens compared with the version it was made on; **Fixed — resolve** (<kbd>E</kbd>) resolves it and moves on to
the next, on whichever screen it is, **Not yet — reply** answers it, and <kbd>]</kbd> and <kbd>[</kbd> skip forward and
back. The strip at the top counts how far you are and switches between **To verify** (screens that changed since their
feedback — where it starts, when there are any), **Waiting** (feedback on screens that have not changed: the fix has not
been run yet, or did not change the screen) and **All open**. A change request without a comment shows the image it was
asked on beside the screen now, and approving the screen settles it. Resolving keeps the list it started with, so the
count holds still; at the end it says what was resolved and offers to go through what is still open. The link keeps the
mode (`/library?resolve=verify`).

**Filter** narrows the flows by state and by test case [priority](/docs/using/test-cases#priority-in-the-library) — any
value within one, every one that is set. A flow that passes shows its whole journey, with the screens that do not match
stepped back. **Display** holds everything about how they are laid out: the folders (test case suites or spec files),
grouping (by folder, state or priority), order (by suite, priority, urgency, most recently captured or most open
comments), the variant and the screen size. The rail on the left — views and the folder tree — stays in reach while the
flows scroll, and a button at the bottom right takes a long library back to the top.

**Views** keep a combination: **Open feedback**, **To fix** (a developer's open feedback, by priority), **To verify**
and **To review** (updated screens, unreviewed ones and feedback to verify) are there for everyone. **+** beside *Your
views* opens the view builder: a name, the states and priorities it shows, its folders, grouping, order and variant, and
how many flows it would hold as you choose. Change what is on screen and **Save view** opens the builder with it; a
changed view can also be saved into itself or reset. A view's menu edits, duplicates, renames or deletes it — built-in
views can be duplicated into one of your own. Your views are yours: nobody else sees them. Everything on screen is in
the link, so a filtered library can be shared as it is.

**Compare with…** in the library measures every screen against another branch or pull request: what differs is boxed
and measured on the storyboard, a screen that is the same says so, and the viewer offers the comparisons with the other
line of work. Useful to show a product owner what a pull request changes compared with `main`.

Admins and members can change the library; viewers browse it. Links to a reference (`/library?ref=pr:212`) work for
references nobody kept, too.

The image a person approved last for each checkpoint is its baseline and is kept by the
[artifact retention](/docs/administration/retention) policy, however old it is — as are the screens the library shows
(the default branch's too, whether or not anybody kept it, with the capture before each screen that tells an updated one
from an unchanged one) and the runs pinned in it, unless an admin lets library screens expire. Data retention never
deletes a run holding any of these.

## For AI assistants

`list_review_checkpoints` answers what changed in a run and by how much (the measured change, and whether the
tolerance approved it), `get_review_checkpoint` attaches an image with its baseline and close-ups of its largest
changed regions so the assistant can look at exactly what changed, and — with a write-scoped token — `review_checkpoint` approves or asks for changes.
An agent that changed the UI can check its own work before you do.

Comments reach the assistant the way you placed them: `get_review_checkpoint` draws the open threads on the image as
numbered pins (and the areas they mark), attaches a close-up of each pin, and lists the threads by the same numbers —
so "#2: the totals lost their border" points at a place on the page. `list_review_threads` lists a run's open threads
with their positions in pixels, percent and CSS pixels. With a write-scoped token, `comment_on_review` pins a thread or
replies to one, and `resolve_review_thread` resolves it. What an assistant writes shows as an AI agent's comment — its name (pass `agent`, e.g. "Codex"; an OAuth app's own name otherwise), a robot avatar and an **Agent** badge — for the person whose access it used, so a reported fix is never mistaken for a colleague's word. The comment list shows an agent's latest reply on the thread's row. Ask it to fix the open
comments of a run, and it can reply with what it changed for you to check — when you tell it to; a write-scoped token
alone does not make it post.

To fix the product from its feedback, an assistant starts with `list_feedback_requests` for the branch you work on:
every open request, one record each — comment threads and "changes requested" without a comment, including screens a
partial run skipped — with the test that produces the image (id, full title, file, browser), the checkpoint key to
search the spec for, the image now and the one the request was made on, and whether it still waits for a fix or changed
since (to verify). Its `producers` are the tests a narrow re-run selects, no more; `get_rerun_command` gives anchored
selectors and a `--list` preview to check the selection before running it. `get_review_checkpoint` compares with what
you choose — `against: "origin"` (the image a request was made on), `"baseline"` or `"previous"` — and says which one
it attached; with `images: "focus"` and a thread it sends only that spot, then and now, which stays readable on a tall
page. `maxImages` bounds the images of one answer, and `attachedImages` says what each one shows. A passed test or a
changed image is evidence, not approval: resolving and approving stay with you.

`list_library` names the references in the library and the run each shows; `get_library_flows` lists a reference's
flows and checkpoints, with capture ids to look at, each screen's state and open comments, and the link to hand a
person — filtered by `state`, `priority` or a `view` ("show me what is ready to verify", `view: "to-fix"`).
`list_review_threads` with `library: true` lists the open comments of every screen a branch shows, not just one run's,
and `placement: "outdated"` the ones made on an earlier version: with `placedOnCapture`, `get_review_checkpoint` shows
the version the comment was about. With a write-scoped token,
`set_library_reference` keeps a pull request in the library, pins its run or makes it the default. The [REST API](/docs/api)
has the same reads under `/runs/{run}/review-checkpoints`, `/review-captures/{capture}` (with `annotatedImageUrl`, the
image with its pins drawn on it), `/feedback-requests`, `/review-threads`, `/library` and `/library/flows`, and — with a write-scoped token —
the same changes: `POST /review-captures/decisions` approves or asks for changes, `POST /review-threads` pins a comment
or replies, `POST /review-threads/status` resolves or reopens one, and `POST /library/references` keeps, pins or names
a reference.
